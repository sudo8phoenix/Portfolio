COMPUTER VISION / PRODUCT / CASE STUDY 03

Fridge Vision

Turn a fridge photo into ingredients you can use.

An image-to-recipe application that connects food detection, rough quantity estimates and optional label reading to a recipe recommendation interface.

Python · FastAPI · YOLOv11-L · OpenCV · EasyOCR · React · Vite

View repository ↗

01 / THE PROBLEM

Connect the pieces into a usable workflow.

A food detector produces labels and bounding boxes, but that output alone does not help someone decide what to cook. Fridge Vision structures detected ingredients and carries them into recipe matching, with a frontend for uploading images and browsing the results.

02 / SYSTEM ARCHITECTURE

Follow the data.

Conceptual flow, based on the repository documentation.

  1. 01

    Upload image

    React sends the image to the combined FastAPI detection-and-recommendation endpoint.

  2. 02

    Detect ingredients

    YOLOv11-L predicts food classes and bounding boxes; OCR can read visible labels.

  3. 03

    Structure output

    Ingredient labels and simple bounding-box quantity estimates feed recommendation logic.

  4. 04

    Find recipes

    Local keyword matching returns recipes; optional Ollama generation offers another path.

Compared with a detector-only notebook, this project connects inference to an API and a complete upload-to-recipe interface. Separating local recipe matching from optional generation also makes the recommendation path more flexible. The docs do not establish an accuracy improvement over other detectors or recipe systems.

03 / ENGINEERING DECISIONS

Why it works this way.

Make the pipeline usable as an API

Separate detection and recommendation endpoints sit alongside a combined endpoint. This supports inspecting individual stages and using the complete workflow from the frontend.

Keep a local recommendation path

Keyword matching can recommend recipes without calling a language model. Optional Ollama generation is an additional mode rather than a dependency of every request.

Configure model behavior centrally

The documented defaults use an 800-pixel inference size, 0.25 confidence threshold and 0.5 IoU threshold. Model paths and thresholds are configurable instead of being coupled to interface code.

Treat vision outputs as product inputs

Ingredient and recipe components make structured model outputs visible to the user. Optional OCR adds a way to use package text when a visual food label alone is insufficient.

04 / EVIDENCE & LIMITS

What the docs establish.

67Configured food classes
800 pxDefault inference image size
0.25Default confidence threshold
0.5Default IoU threshold

These numbers describe the configured model and inference settings, not measured accuracy. The README identifies YOLOv11-L weights and the frontend/API integration but does not report mAP, per-class precision and recall, or end-to-end latency.

Tradeoffs & next validation

Bounding-box estimates are rough quantities, not measured ingredient weight or volume. Occlusion, lighting and packaging can affect detection. A held-out image evaluation, recipe relevance assessment and latency measurements would be needed to quantify how well the whole system works.
