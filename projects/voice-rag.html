01 / THE PROBLEM

What needed solving.

Documents arrive in different formats, while people may prefer speaking to typing. A reusable retrieval system must normalize inputs, select relevant context and keep speech handling separate from retrieval and generation.

03 / ENGINEERING

The decisions behind it.

Make stages replaceable

Parser, chunker, embedding, retrieval, model and speech modules have separate boundaries. Per-format chunking and YAML configuration let the pipeline adapt to the corpus.

Retrieve broadly, then rerank

Dense retrieval can combine with BM25, followed by a cross-encoder. Chroma is the default vector store; FAISS and Qdrant are configurable alternatives.

Keep voice optional

Whisper variants handle transcription, and configurable TTS engines provide output. Text mode and muted speech remain available. Ollama supports a local runtime; Groq is an optional hosted provider.

Text + voiceInput and response workflows

The README documents end-to-end orchestration through PipelineOrchestrator and Gradio, with multi-format parsers, configurable chunkers, hybrid retrieval and reranking. It reports implementation and tests, without a fixed-corpus Recall@k or grounded-answer benchmark.

Current limits & next validation

Retrieval quality depends on corpus preparation, chunking and model choice. A useful next evaluation compares dense, hybrid and reranked retrieval on the same fixed questions and sources, with answer grounding and end-to-end latency measured separately.
