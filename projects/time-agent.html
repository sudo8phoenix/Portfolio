APPLIED AI / CONSTRUCTION / CASE STUDY 01

Time Agent

Progress updates you can trace back to evidence.

A local-first assistant that turns daily construction reports into reviewable schedule updates. The model proposes a change; a human decides whether it enters the progress ledger.

Python · FastAPI · PostgreSQL · React · LangGraph · Ollama

01 / THE PROBLEM

Reports need a reliable path to progress.

Daily reports describe work in natural language, while schedules track structured activities. Connecting the two requires more than extracting a number: the system must preserve the source, distinguish planned work from completed work, and handle uncertain matches without silently changing project progress.

02 / SYSTEM ARCHITECTURE

Follow the data.

Conceptual flow, based on the repository documentation.

  1. 01

    Import & stage

    Schedules retain source IDs, versions and provenance before explicit activation.

  2. 02

    Process report

    FastAPI persists a job; a leased LangGraph worker extracts and validates evidence.

  3. 03

    Match & propose

    The configured model discovers candidates and selects supported schedule matches.

  4. 04

    Review & record

    A reviewer approves the proposal before the deterministic ledger changes.

Compared with a direct report-to-percentage script, this architecture adds a review boundary, provenance and recovery. Its engineering advantage is a more inspectable update process—not a claim that an LLM can reliably run a construction schedule on its own.

03 / ENGINEERING DECISIONS

Why it works this way.

Keep approval outside the agent

The agent can persist pending proposals but cannot approve them, activate schedules or write progress events directly. This gives the model a useful role without handing it control over the official record.

Recover through durable checkpoints

PostgreSQL stores both jobs and graph checkpoints. Leases govern execution, and idempotent persistence protects against duplicate proposals after a restart or an uncertain commit outcome.

Preserve the chain of evidence

Source references, schedule versions, corrections and review history travel with the proposed change. A reviewer can investigate why a match was suggested and trace approved effects through history and export.

Keep model controls on the server

Inference runs locally or through a private authenticated Ollama endpoint. Browser input cannot replace endpoints, prompts, tools or checkpoints; public traces expose bounded metadata rather than report bodies.

What the docs establish.

The documented 12 October 2026 Gemma 4 12B benchmark used 60 existing synthetic cases and supplied the full schedule. Five unmatched cases were falsely assigned activities. This compact benchmark differs from the production graph pipeline; independent label review and a complete unseen UI-to-export evaluation remain pending. Workflow smoke checks produced pending proposals and no approved events.

Tradeoffs & next validation

Checkpoint and browser-to-worker checks establish bounded workflow behavior, not model accuracy. Real field reports, independently adjudicated labels and complete production quality evaluation are still needed. The documented Qwen and Gemma runs use different prompts and context, so they do not support a fair model ranking.
